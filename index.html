Branching strategies when agents write the code

Many AI agents work in parallel, each on its own ticket, and every change goes through a pull request. Two branching models handle that well. You will step through both, build a release yourself, and finish with a short quiz.

Trunk-based: internal products, ship constantly Selective promotion: client work, partial releases

Shared foundation

Four habits both models rely on

The models differ in where work is integrated. The way each ticket is isolated and landed is the same.

One worktree, one branch per ticket

Each agent gets its own folder on disk, so parallel agents never overwrite each other's files.

Short-lived ticket branches

A branch exists to land one ticket. The longer it lives, the more it drifts from its base.

Pull requests are the gate

CI and review run on the PR. Nothing reaches a shared branch without passing it.

Squash merge agent work

Agents commit exploratory steps. A squash turns them into one readable commit per ticket.

Model 1

      
Trunk-based development

      
Use it for internal products and services that deploy several times a day. There is one long-lived branch, main, and it must always be releasable. Every ticket lives on a branch for hours, or two days at most, then lands on main. Unfinished features hide behind feature flags. There is no develop or uat branch.

    

    

  


  

    

      
Model 2

      
Selective promotion

      
Use it for client work where each ticket has its own branch, tickets are tested together on UAT, and the client may release only some of them. The final pull request must still land on main.

      
At release time the person in charge cuts a fresh release/* branch from main, squash-merges only the approved tickets into it, and opens one PR to main. Choose which tickets the client approved, then step through.

    

    

    

      
Why a release branch beats separate PRs

      
Compare the two modes above using the same approved tickets. With a release branch, conflicts between tickets are resolved once, in one place, and main gets exactly one clean commit per approved ticket. With separate PRs, each ticket must be rebased onto the result of the one before it, and the conflicts are resolved on main itself, one at a time.

    

  


  

    

      
Side by side

      
Choose by project constraints

      
Classic Git Flow, with long-lived develop, release and hotfix branches, adds too much overhead and merge pain when many agents produce changes at once. These two models keep the useful parts and drop the rest.

Pick trunk-based when
You own the product, deploy often, and can hide unfinished work behind flags.

      
Pick selective promotion when
A client tests on UAT and can approve some tickets while rejecting others.

    

    
Both keep ticket branches current by rebasing or merging from their base while they are active, use consistent names such as ticket/<id>-short-desc, and automate worktree creation and cleanup.
