The history most teams already have

Shared foundation

Four rules both models share

One worktree, one branch per ticket

Each agent gets its own folder. Parallel agents cannot overwrite each other.

Short-lived ticket branches

A branch exists to land one ticket. Long-lived branches drift from their base.

Pull requests are the gate

CI and review run on the PR. Nothing reaches a shared branch without them.

Squash merge agent work

Many small agent commits become one commit per ticket.

Model 1

      
Trunk-based development

      
For internal products that deploy several times a day. main is the only long-lived branch and is always releasable. A ticket branch lives for hours, two days at most. Unfinished features sit behind feature flags.

    

    

    

      
Critical rule

      
Never commit to a branch after its PR has been merged

      
After a squash merge, the branch's old commits are unrelated to main. New commits on that branch bring the shipped work back into the next PR and conflict with the squash commit.

      
Instead: delete the branch and worktree when the PR merges. Start follow-up work on a new branch from the latest main.

      
git worktree add -b ticket/101-login-fix ../worktrees/101b origin/main

    

  


  

    

      
Model 2

      
Selective promotion

      
For client work: one branch per ticket, testing on UAT, and the client may release only some tickets. The final PR must land on main.

      
At release, cut release/* from main. Each approved ticket gets a PR into it (squash merge). One final PR lands on main with Rebase and merge: one commit per ticket, no merge commit.

    

    

    

      
Why not PRs straight to main?

      
Conflicts get fixed on main one PR at a time, by hand, and never tested on uat. A release branch lets you fix them once and test the result before it lands.

    

  


  

    

      
Side by side

      
Choose by project constraints

      
Git Flow (long-lived develop, release and hotfix branches) creates too much merge overhead for parallel agents. Pick by project constraints.

Pick trunk-based when
You own the product, deploy often, and can hide unfinished work behind flags.

      
Pick selective promotion when
A client tests on UAT and can approve some tickets while rejecting others.

    

    
Both keep branches current by rebasing, name them ticket/<id>-short-desc, and automate worktree setup and cleanup.
